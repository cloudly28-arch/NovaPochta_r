# Backend оптового склада «Нова пошта» — документация классов

## 1. Назначение

Этот набор заголовочных файлов задаёт предметную модель backend-части симуляции оптового склада. На данном этапе реализации методов нет: `.h` описывают структуру объектов, их состояние и публичный интерфейс. Реализация будет добавляться позже в соответствующие `.cpp`.

Основная идея архитектуры: backend на C++ хранит состояние склада и принимает решения, а Godot получает уже готовое состояние объектов и отображает его визуально.

## 2. Основные сущности

### `Position`
Простая двумерная координата объекта на складе.

Поля:
- `x` — координата по горизонтали;
- `y` — координата по вертикали.

Используется для работников, транспорта, ячеек, зон и задач.

### `Worker`
Работник склада.

Хранит:
- уникальный ID;
- ФИО;
- роль;
- текущее состояние;
- координаты;
- ID текущего задания.

Работник может быть свободным, занятым, на перерыве или вне смены. В дальнейшем класс будет использоваться системой диспетчеризации заданий.

### `Store`
Магазин или точка, которая получает товар со склада.

Хранит ID, название, адрес и контактный телефон. Заказы ссылаются на магазин через `storeId`.

### `Product`
Карточка товара.

Хранит:
- ID;
- название;
- SKU/артикул;
- вес;
- объём.

Сам класс товара не содержит складской остаток. Остаток хранится отдельно, поскольку один и тот же товар может лежать в разных ячейках.

### `StorageCell`
Конкретная ячейка хранения на складе.

Хранит:
- ID;
- код ячейки;
- координаты;
- максимальную вместимость;
- ID размещённого товара;
- текущее количество.

В будущем методы `putProduct` и `takeProduct` будут контролировать вместимость и корректность операций.

### `WarehouseZone`
Логическая зона склада: приёмка, хранение, комплектование, упаковка или отгрузка.

Хранит геометрию зоны и список ID ячеек, входящих в неё.

### `InventoryItem`
Запись складского остатка.

Связывает:
- товар;
- ячейку;
- количество.

Это позволяет одному товару находиться сразу в нескольких местах.

### `OrderItem`
Одна строка заказа: какой товар и в каком количестве нужен.

### `Order`
Заказ магазина.

Содержит:
- ID заказа;
- ID магазина;
- статус;
- время создания;
- список позиций `OrderItem`.

Жизненный цикл заказа задаётся через `OrderStatus`: от создания до завершения или отмены.

### `WarehouseTask`
Рабочее задание внутри склада.

Например:
- принять товар;
- разместить товар;
- собрать товар;
- переместить товар;
- упаковать заказ;
- загрузить машину.

Задание знает исполнителя, товар, количество, исходную и целевую позицию, а при необходимости связано с заказом.

### `Vehicle`
Транспортное средство или внутрискладская техника.

На первом этапе хранит ID, модель, грузоподъёмность, доступность и координаты. Позже этот класс можно расширить до погрузчиков, тележек и грузовых машин.

### `Warehouse`
Главный агрегирующий класс системы.

Он содержит коллекции:
- работников;
- магазинов;
- товаров;
- ячеек;
- зон;
- остатков;
- заказов;
- заданий;
- транспорта.

Через него backend получает единое состояние склада. В дальнейшем сюда можно добавить сервисные методы: создание заказов, приём поставки, резервирование остатков, назначение задач и т.д.

### `Simulation`
Контроллер времени симуляции.

Хранит ссылку на `Warehouse`, текущее модельное время, множитель скорости и состояние запуска. Метод `update(deltaTime)` в будущем будет выполнять один шаг модели.

## 3. Перечисления

Все основные перечисления находятся в `Types.h`.

### `WorkerRole`
Роли работников:
- `Manager`;
- `Storekeeper`;
- `Loader`;
- `Picker`;
- `Driver`;
- `Operator`.

### `WorkerStatus`
Состояния работника:
- `Free`;
- `Busy`;
- `OnBreak`;
- `Offline`.

### `OrderStatus`
Статусы заказа:
- `Created`;
- `Accepted`;
- `InProgress`;
- `ReadyForShipment`;
- `Shipped`;
- `Completed`;
- `Cancelled`.

### `TaskType`
Типы внутренних операций склада.

### `TaskStatus`
Статусы выполнения задания.

### `ZoneType`
Типы зон склада.

## 4. Связи между классами

Упрощённо модель выглядит так:

```text
Warehouse
├── Worker
├── Store
├── Product
├── StorageCell
├── WarehouseZone
├── InventoryItem
├── Order
│   └── OrderItem
├── WarehouseTask
└── Vehicle

Simulation
└── Warehouse
```

Основные ссылки между сущностями сделаны через ID, а не через сырые указатели. Это упрощает сериализацию, хранение в базе данных и передачу состояния во фронтенд.

## 5. Предполагаемый сценарий работы

1. Магазин создаёт `Order`.
2. `Warehouse` проверяет остатки.
3. Для позиций заказа создаются `WarehouseTask`.
4. Свободный `Worker` получает задание.
5. Его координаты обновляются во время симуляции.
6. При достижении ячейки происходит операция с товаром.
7. После комплектации заказ переходит в упаковку и затем в отгрузку.
8. Godot визуализирует позиции, состояния и перемещения, но не принимает бизнес-решения.

## 6. Почему `.h` сейчас без реализации

На этом этапе задача — зафиксировать модель предметной области и интерфейсы классов. Это позволяет сначала согласовать архитектуру, а затем независимо реализовывать методы в `.cpp`.

Рекомендуемый следующий порядок разработки:

1. реализовать простые классы (`Product`, `Store`, `OrderItem`, `Position`);
2. реализовать `StorageCell` и `InventoryItem`;
3. реализовать `Order`;
4. реализовать `Worker` и `WarehouseTask`;
5. реализовать `Warehouse`;
6. реализовать `Simulation`;
7. добавить обмен состоянием с Godot.
